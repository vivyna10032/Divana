## 快速开始

需要 Python 3.13 或更高。下面的命令**显式指定解释器版本**，不要用光秃秃的 `python`：
如果这台机器上装了 Anaconda，`python` 很可能指向它，建出来的环境会跟项目对不上。

```powershell
# 1. 建环境（用 py 启动器指定 3.14）
py -3.14 -m venv .venv

# py -0p 如果列不出 Python，就走官方安装的完整路径：
# & "$env:LOCALAPPDATA\Programs\Python\Python314\python.exe" -m venv .venv

# 2. 激活：之后这个窗口里的 python / pip 都是项目自己的
.\.venv\Scripts\Activate.ps1

# 3. 装依赖
pip install -r requirements.txt

# 版本已经钉死了（openai-agents==0.22.2 这种）。想一字节不差地复现我这台机器的
# 42 个包，用 pip install -r requirements.lock（那个文件里有 pywin32，只能在 Windows 用）

# 4. 配置密钥
Copy-Item .env.example .env
# 打开 .env，填入你的 DIVANA_API_KEY

# 5. 开始聊
python -m divana
```

激活成功后命令行开头会出现 `(.venv)`。**每开一个新窗口都要重新激活一次**，忘了激活就会报
`No module named 'agents'` 这类错。不想激活也行，把命令里的 `python` 换成
`.\.venv\Scripts\python.exe`，效果一样，而且没有歧义。

## 换模型 / 换服务商

密钥、接口地址、模型名都在 `.env` 里，改完重启即可，不需要动代码：

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `DIVANA_API_KEY` | 密钥，必填 | 无 |
| `DIVANA_BASE_URL` | 接口地址 | `https://api.deepseek.com` |
| `DIVANA_MODEL` | 模型名 | `deepseek-v4-pro` |

当前 DeepSeek 接口可用的模型名是 `deepseek-v4-pro` 和 `deepseek-flash`。
换成其它 OpenAI 兼容服务时，把 `DIVANA_BASE_URL` 和 `DIVANA_MODEL` 一起改掉就行。

## 联网搜索（可选）

不配也能用，只是她遇到不确定的事只能说不确定，查不了。

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `DIVANA_SEARCH_PROVIDER` | 服务商，三选一：`tavily` / `brave` / `serper` | `tavily` |
| `DIVANA_SEARCH_API_KEY` | 对应服务商的 key | 空（等于关闭搜索） |
| `DIVANA_SEARCH_MAX_RESULTS` | 每次搜索取几条 | `5` |

Tavily 在 [tavily.com](https://tavily.com) 注册就有免费额度，把 key 填进 `.env` 即可。
换服务商只改 `DIVANA_SEARCH_PROVIDER`——三个适配器都在 `divana/search.py` 里，
想接新的照抄一段就行。

## GitHub 配额（走代理的话建议配）

GitHub 未登录调 API 是 **60 次/小时**，而且**按你的出口 IP 算**。走代理的话，
这 60 次是同一个节点上所有人共享的——经常整天都是 403，看起来像"仓库不存在"。

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `DIVANA_GITHUB_TOKEN` | 配额提到 **5000 次/小时**，且按 token 算、不看 IP | 空（匿名） |

这个 token **不需要任何权限**：公开仓库匿名就能读，它纯粹用来提高配额。生成路径：
GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens，
勾一个 "Public Repositories (read-only)" 就够。

代码层面还省了一半配额：README 走 `raw.githubusercontent.com`（**那个域名不计入
API 配额**），只有文件名不标准时才退回 API 端点。所以现在读一个仓库只用 1 次 API。

## 自检

两个检查，按顺序跑就行。都不写文件，随便跑。

**一、环境对不对**（不联网，秒出）：

```powershell
python -m scripts.check_env
```

它会告诉你当前跑的是哪个 Python、是不是项目的 `.venv`、依赖装没装、`.env` 里的 key 读到没有。
最后一行是结论，有问题的项会编号列出来。

它还会**真的构造一遍工具定义**——这一步能抓住一类很隐蔽的错误：openai-agents 默认给
工具参数开 strict JSON Schema，参数类型写得太自由（比如用 `dict`）会在定义工具的那一刻
就抛错，平时看不出来，一跑就是"启动/评测报错"。改完 `tools.py` 顺手跑一下这个检查。

**二、模型通不通**（要联网，会花一点 token）：

```powershell
python -m scripts.smoke_test
```

它会打印当前用的模型和接口地址，然后让 Divana 自我介绍一句。

**三、纯逻辑对不对**（不联网，秒出）：

```powershell
python -m unittest discover -s tests -v
```

画像、笔记读写、搜索解析、配置解析、instructions 拼装的离线单测，
不需要 key 也不需要网络。
改这几个模块就顺手跑一下——它们占了项目一多半的逻辑。

报 `No module named ...` 基本都是"忘了激活环境"，回到快速开始第 2 步。

里面还有一组**网页层的测试**：起一个真服务器，用一个假 service 把 HTTP 和 SSE
跑一遍（它需要 starlette，没有就自动跳过）。

## 持续集成

`.github/workflows/tests.yml`：push 到 main、以及每个 PR，都会在 GitHub 上自动跑
**528 条离线测试**（Python 3.13，Linux）。

**只跑不花钱的那一层。** 评测（20 条用例）故意不进 CI：它要真调模型，一轮约 0.37 元，
而且结果本身是概率性的——放进 CI 就变成"每次 push 都可能红，还得盯着分辨是真挂还是抖动"。
评测是**发布前手跑**的清单，不是 push 的门槛。**能自动的自动，要花钱的留给人决定。**

两条口径写在 workflow 的注释里，这里也说一遍：

- 跑的是 **Python 3.13**，也就是 README 里写的最低版本——顺手守住"最低版本也能跑"这条线
  （开发机上是 3.14.2）。
- 只跑 Linux。项目主要运行在 Windows，但离线测试里没有平台假设（文件一律走临时目录、
  编码显式写 UTF-8），所以 Linux 全绿就说明代码是干净的。要覆盖 Windows，
  把 `windows-latest` 加进那个 matrix 就行。

CI 里的最后一步会跑 `divana.evals --history` 和 `--calibrate`——它们不需要 API key、
不调模型，只验证这两个命令行入口没被改坏。

## 她的记忆

"记忆"其实是四份不同的东西，分工完全不同，这也是理解 agent 的一个好切口：

| 层 | 存在哪 | 装什么 | 怎么进模型 |
| --- | --- | --- | --- |
| 会话存档 | `data/divana.db` | 每轮对话的原样记录 | 只带最近若干条（见 `divana/session.py` 的 `HISTORY_LIMIT`） |
| 学习者画像 | `vault/profile.md` | 提炼过的结论：目标、水平、薄弱点… | 每轮都拼进 system prompt |
| 学习笔记 | `vault/notes/*.md` | 一个个概念，带出处 | 不进上下文，靠 `search_notes` / `read_note` 自己翻 |
| 学习计划 | `vault/plan.md` | 现在的位置 / 下一步 / 路线图 / 复盘记录 | 不进上下文，聊到方向时她自己读 |

**会话存档**：聊完自动落库，关掉窗口再启动就是接着上次聊。想开一段新记忆，换个会话名：

```powershell
python -m divana --session 2026-09
```

数据库里始终是全量记录，`HISTORY_LIMIT` 限制的只是"每次带多少进模型"——
聊得越久成本越高，这个上限就是刹车。

**学习者画像**：分五节（目标 / 当前水平 / 已掌握 / 薄弱点 / 学习习惯）。
她在聊到关于你自己的、以后还用得上的信息时会自己更新，并告诉你记了什么。
你也可以直接手改这个文件，她下次启动读到的就是最新版本；终端里输入 `/profile` 可以随时查看。

> 记画像有个前提：**先回答问题，再顺手记**。2026-09-24 踩过一次——你问"帮我讲清楚
> embedding 是什么"，她只调了一次 `update_learner_profile`，把解释写进了画像文件，
> 然后对你说"我记进画像了，要不要存成笔记"。**答案是写进文件了，你一个字没看到。**
> 根因是 prompt 只写了"要记 / 要问 / 要答"，没写谁先谁后，而工具返回那句
> "记得用一句话告诉用户你记了什么"位置最靠后、最抢戏。现在 prompt 和工具返回
> 都补了优先级：记录是顺带的，不许顶替回答。

**学习笔记**：聊到一个值得留下的概念，她会问一句"要不要存成笔记"，你说好，
她就写成 `vault/notes/日期-标题.md`，带 `title / date / tags` 的 front-matter，
Obsidian 打开就能用。同名不会覆盖，会加 `-2`、`-3`。

三层记忆的分工是刻意的：**画像必须每轮都在眼前，所以它得小；笔记可以有很多，
所以它不进上下文，靠工具按需去取。** 什么该塞进 prompt、什么该做成工具按需查，
是 agent 工程里最常要权衡的一件事。

这些文件是**并发安全**的，因为 SDK 把同步工具丢进线程池跑（`asyncio.to_thread`）
——模型一次要求调两个 `update_plan`，那就是**两个线程同时改同一个文件**。三层保护：

1. **唯一的临时文件名**：不然两个写者抢同一个 `xxx.md.tmp`，一个把 tmp 换走、另一个
   找不到它（WinError 32），目标还可能被写成半截。
2. **按路径的写锁**：`write_section` 是"读整份 → 改一节 → 写整份"，不加锁的话两个
   写者各自基于同一份旧快照写回去，后写的把先写的整个盖掉。
3. **替换时退避重试**：Windows 上 `os.replace` 会因为"目标正被占用"直接拒绝
   （WinError 5）——占用者可能是另一个线程，也可能是 Obsidian / 编辑器 / 杀毒软件。

> 2026-09-24 的真实事故：模型一次要求改计划的两节（并行两个工具），工具都返回了
> "已更新"，可文件里**少了"里程碑打勾"**——三层保护里前两层都缺。这件事是评测的
> 文件断言抓出来的：如果只断言"她调了 update_plan"，它会一直安静地丢数据。

## 终端里的命令

在 `python -m divana` 里直接输入：

| 命令 | 作用 |
| --- | --- |
| `/profile` | 看 Divana 记了你什么（也可以直接编辑那个文件） |
| `/plan` | 看当前的学习计划（也可以直接编辑那个文件） |
| `/notes` | 列出手上的笔记 |
| `/search 关键词` | 不走模型，直接试一次联网搜索 |
| `/summary` | 把这次对话整理成一篇笔记（要花一次模型调用） |
| `exit` | 退出（`quit`、`退出` 也行），退出前会问一句要不要整理成笔记 |

`/search` 存在的意义是**把两个问题分开**："搜索本身通不通"和"模型会不会去调它"。
排查的时候这两件事必须能单独验证，否则你永远不知道是哪一环坏了。

启动信息里有三行也值得看一眼：

```
  配置来源: D:\CodexProjects\divana\.env（最后修改 2026-09-13 19:09）
  学习者画像: D:\CodexProjects\divana\vault\profile.md
  联网搜索: tavily（没配 key，遇到不确定的事只会说不确定）
```

`配置来源` 会告诉你读的是哪个 `.env`、最后什么时候改的；`联网搜索` 会区分
"服务商不认识""没配 key""已配置"三种情况。**"我明明填了却没生效"这类问题，先看这两行**——
实际经验里，九成是改错了文件、忘了保存，或者等号后面没粘上真正的值。

## 代码分层

```
vault/  data/        数据：画像、计划、笔记、对话存档
divana/*.py          能力：搜索、读材料、总结、规划……每个模块只干一件事
divana/service.py    服务层：把能力组合成"问一句 / 总结 / 看计划"这样的动作
divana/cli.py        显示层：读键盘、打印——唯一知道"终端"存在的地方
```

显示层只认服务层，服务层完全不认显示层。所以接前端时只需要**再写一个显示层**
（网页），能力一个字都不用动。**这就是为什么"抽服务层"是做前端的第一步，
而不是做完前端之后的整理工作。**

服务层返回的是**结构化数据**（`Reply` 里带回答文本、以及这轮调用了哪些工具），
不是打印好的字符串——网页想画成卡片、终端想打一行，都随调用方。

CLI 现在还有个 `--stream` 开关，加上它会边生成边显示（打字机效果）：

```powershell
python -m divana --stream
```

默认不开。因为它是一条比较新的代码路径（走 SDK 的流式接口），先用验证过的
非流式跑；想出问题也好定位。

## 网页版

```powershell
python -m divana.webapp
```

然后浏览器打开 **http://127.0.0.1:8765**。左边是导航，现在两个页面：

- **对话**：聊天（带打字机效果），右边四块只读内容（学习目标 / 现在的位置 /
  下一步 / 最近的笔记）。输入框上方有三个快捷提问按钮——它们是把 prompt 里
  那些规则摆到台面上，省得你不知道能问什么。右下角还有"整理成笔记"按钮，
  因为网页没有"退出时询问"那个环节。
  左侧是**会话列表**：列出所有聊过的对话（标题取第一句话、时间转成本地时区），
  可以新建对话、点进去切换，切换时会把这个会话的历史载入进来。
- **学习计划**：左边按阶段列出路线图，已完成的打勾、没完成的留空，当前阶段带标记；
  右边是进度条、"已完成 5 / 11"、现在的位置、下一步、复盘记录。
  **进度是从 markdown 的 checkbox 里真数出来的**，不是估的。
- **知识库**：左边是笔记列表，支持关键词搜索和标签筛选；右边读全文。
- **学习画像**：五节正文（目标 / 当前水平 / 已掌握 / 薄弱点 / 学习习惯）摊开成卡片，
  右边是里程碑进度和"这份画像是怎么来的"（文件在哪、什么时候更新的、
  以及一句提醒：手改画像要重启服务她才会读到）。

四个页面到这里齐了：对话、学习计划、知识库、学习画像。

页面文件拆成了几个：`web/index.html`（结构）、`web/style.css`（样式）、
`web/app.js`（逻辑）、`web/markdown.js`（渲染），由 Starlette 的静态文件挂载提供。
**依然没有构建步骤**，改完刷新就生效。

`markdown.js` 单独放是有原因的：它不碰 DOM，纯字符串进、纯 HTML 出。所以
`tests/test_webapp.py` 可以用 node 直接把它 require 进来跑断言——包括"模型输出的
HTML 必须被转义"这条安全断言。跟 Python 那边把纯逻辑和框架胶水分开是同一个道理。
目前支持：标题、列表、引用、**表格**、代码块、加粗、行内代码、链接。

**它只监听本机（127.0.0.1）**，别改成 `0.0.0.0`：这个服务能读你本地的文件、
用你的 API key，暴露到局域网就等于把它们交出去。

它和命令行共用同一套东西——同一个 service 层、同一个会话库、同一份画像和笔记，
所以你在这边聊的，那边也记得。只是一次别同时在两个进程里聊同一场对话，
两边的历史会互相插话。

顺带说下为什么用 Starlette 而不是 FastAPI：**环境里本来就有**（openai-agents
通过 mcp 带进来的），不用装任何东西；而且 Starlette 就是 FastAPI 底下那一层，
路由写法几乎一样，想换随时能换。

## 她会做的事（工具）

模型自己能做的只有"说话"。要动手就得有工具——每个工具对应 `divana/tools.py` 里的一个函数：

| 工具 | 做什么 | 动到哪 |
| --- | --- | --- |
| `update_learner_profile` | 更新画像的某一节 | `vault/profile.md` |
| `read_plan` | 看当前的学习计划 | `vault/plan.md` |
| `update_plan` | 更新计划的一节或多节（`updates` 是一个列表，每项写 section + content） | `vault/plan.md` |
| `make_quiz` | 出一份小测并存下参考答案 | `data/practice.json` |
| `grade_quiz` | 批改这次小测，错题汇总写进「复盘记录」 | `data/practice.json` + `vault/plan.md` |
| `search_web` | 联网查证 | 搜索服务商 |
| `save_note` | 把一个概念存成笔记 | `vault/notes/` |
| `search_notes` | 翻自己的笔记（传 `*` = 列出全部） | `vault/notes/` |
| `read_note` | 读某篇笔记的全文 | `vault/notes/` |
| `read_url` | 读网页正文 | 网络 |
| `read_github_repo` | 读 GitHub 仓库（元信息 + README） | GitHub API |
| `read_arxiv_paper` | 读 arXiv 论文（元信息 + 摘要 + 正文） | arXiv API |

工具的名字、描述（就是函数的 docstring）和参数类型，合起来是**给模型的说明书**——
模型看不到函数体，它只能靠这三样判断什么时候该调、参数怎么填。
所以**改工具说明就等于改她的行为**，而且它通常比改人格 prompt 更直接、更容易验证。

## 学习计划（v0.5 前半）

`vault/plan.md` 分四节：**现在的位置 / 下一步 / 路线图 / 复盘记录**。
终端里输入 `/plan` 可以随时看，也可以直接编辑那个文件。

它和画像的分工不一样，这个差别是刻意的：

| | 内容 | 进不进 instructions |
| --- | --- | --- |
| 学习者画像 | 你是谁、学到哪了（短、稳定） | **进**，每轮都在眼前 |
| 学习计划 | 接下来怎么走（会长、会改） | **不进**，聊到方向时她自己读 |

这是"上下文预算"这同一条取舍的第三次应用（前两次是画像 vs 笔记、笔记摘要 vs 全文）。
实际效果：你问"接下来学什么"，她会先 `read_plan` 再回答；你说"这个我学会了"，
她会把里程碑勾成 `- [x]`，并把下一件事提到"下一步"。

而且她做规划时有个硬要求：**必须基于画像和笔记**（你的目标、水平、学过什么），
不许凭空给一份通用学习路线——那种东西你问任何一个 AI 都有。

## 读外部材料（项目 / 论文 / 网页）

丢给她一个仓库地址、论文编号或者文章链接，她读进来再讲：

```text
帮我总结一下 https://github.com/openai/openai-agents-python
1706.03762 这篇论文讲了什么？
https://example.com/some-post 这篇博客的核心观点是什么
```

三条路线是分开的，因为"怎么拿到内容"完全不同：

| 材料 | 怎么读 | 为什么这么读 |
| --- | --- | --- |
| GitHub 仓库 | 官方 REST API（元信息 + raw README） | 仓库页面是 JS 渲染的，抓 HTML 只能拿到一堆脚本 |
| arXiv 论文 | 官方 Atom API（元信息 + 摘要）+ `arxiv.org/html/{id}` 拿正文 | 摘要够速览，正文拿得到就更深一层 |
| 其它网页 | 直接抓 HTML，去脚本样式后抽正文 | 没有 API 可用，只能这样 |

总结的结构（一句话 / 怎么做的 / 值得看的地方 / 局限 / 跟你有关 / 出处）写在
`prompts/divana.md` 里，想改格式就改那里。

几个已知边界，遇到别以为是坏了：

- **JS 渲染的页面抓不到东西**，她会明说"抓下来是空的"，而不是编内容
- **一份材料最多 12000 字**，超了会截断并标注，所以论文通常只覆盖到摘要和开头
- **arXiv 的旧论文可能没有 HTML 版**，那就只用摘要讲
- **只允许 http/https**：`file:///...` 会被挡掉——防的是她被网页里的话带着去读你本地的文件
- **GitHub 匿名配额是 60 次/小时，且按出口 IP 算**：走代理容易被同一个节点的别人用光。
  撞上时她会告诉你大概多久恢复、以及怎么彻底解决（见上面那节）

## 回顾一次对话（v0.4 后半）

聊完一场，她可以把这次对话整理成一篇结构化笔记，存进 `vault/notes/`——
所以以后用 `search_notes` 也翻得到。两种触发方式：

- **退出时问一句**："要不要把这次对话整理成一篇笔记？(y/N)"。默认不整理，你说了算
- **随时手动**：在对话里输入 `/summary`

为什么这件事需要**第二个 agent**，而"读项目/论文"不需要？这是理解 agent 分工的一个好切口：

| | 素材在哪 | 主 agent 看得到吗 |
| --- | --- | --- |
| 读项目 / 论文 | 刚抓进来的内容 | 看得到，就在它眼前——**不需要第二个 agent** |
| 回顾这次对话 | `data/divana.db` | **看不到**，它的上下文只有最近 40 条——所以要另起一个 |

总结者（`prompts/summarizer.md`）是一个**没有工具、指令完全不同**的 agent，
拿到的是从会话库还原出来的完整对话文本。它跑的时候不传 session，所以这次旁路调用
不会写回对话、也不影响正在进行的上下文。

**这就是多 agent 最朴素的形式：不是"多个角色在聊天"，而是不同任务用不同的上下文和不同的指令。**

## 复盘（v0.8 前半）

```powershell
python -m divana.review          # 手动跑一次
```

也可以在学习计划页点**做一次复盘**按钮。它做的事：把最近 7 天的对话、当前计划、
画像、最近的笔记拼成一份材料，交给一个**专门的复盘者**（`prompts/reviewer.md`），
产出一段复盘，**追加**到计划的"复盘记录"里。

为什么要专门开一个 agent？和"总结一次对话"同一个理由：**素材不在主 agent 的视野里**。
它只看得到当前会话的最近 40 条，而复盘要横跨所有会话、按时间过滤，还得同时看着计划和画像。

三个实现细节值得知道：

- **追加而不是替换**。复盘记录是日记，只增不改，所以 store 里多了 `append_to_section`，
  和 `write_section`（整体替换，用在画像那种"提炼出来的视图"上）分工明确。
  用替换的语义去写日记，会把历史一次冲掉。
- **内容里的二级标题会被降级成三级**（写文件和拼素材时都是）。因为文件结构靠 `##` 切分，
  内容自带 `## 标题` 会造成**静默的结构损坏**：下一次追加会插到它前面，日记顺序就反了，
  而且看起来一切正常。这个 bug 是测试抓出来的。
- **定时任务以后调的是同一个函数**。所以手动跑通了，定时只是换个触发点；
  真出问题也能先手动跑一遍，把"逻辑问题"和"调度问题"分开。

## 定时复盘（v0.8 后半）

网页服务启动时会挂一个后台任务：每 30 分钟看一眼"距上次复盘够 7 天了吗"，够了就自动跑一次。
所以**下次打开服务时它会自己补上**——你电脑关着的那几天不会跑，重新打开就赶上。

学习计划页的"复盘记录"下面会显示一行状态：

```
上次复盘：2026-09-20（3 天前）　·　下次自动复盘：4 天后
```

三个设计决定：

- **按间隔判定，不按"每周几"**：读上次成功复盘的日期，超过 7 天就该跑。这样你不用记得
  上次是哪天跑的，也不会因为"今天不是周日"白等一周。这个日期记在 `data/state.json`，
  **不去解析模型写的日期**——那是猜（它可能没写、可能换格式），而"上次什么时候跑的"
  是程序自己做过的事，程序自己记最可靠。
- **只在服务开着的时候跑**。本地工具的现实就是这样，不假装自己是 7x24 的服务器。
  真需要"电脑关了也跑"，就挂系统级定时任务：

  ```powershell
  python -m divana.review --if-due    # 同一条判定逻辑，重复执行是安全的
  ```

- **失败要留痕，而且要能重试**。后台任务失败最容易静默，所以：失败写进状态文件、
  界面上显示"上次自动复盘失败：..."、并且**不记成功日期**——否则要再等一周才会重试。

## 删除（进回收站，不真删）

网页上现在能删四样东西：**会话、笔记、一次复盘、一个阶段**。入口分别在会话列表
（鼠标移上去出现 ×）、笔记详情右上角、每条复盘右上角、每个阶段右上角。

规矩是**先移进回收站**：

| 删什么 | 怎么处理 |
| --- | --- |
| 会话 | 先把整段对话导出成文件，再从库里删行 |
| 笔记 | 文件**移动**到 `data/trash/`，不是卸载 |
| 一次复盘 / 一个阶段 | 先把那段原文存成文件，再从 plan.md 里移除 |

回收站在 `data/trash/`（在 `.gitignore` 里），文件名前面带删除时间，文件开头写着
"从哪儿删的、什么时候删的"。**它不自动清理**——你自己去看一眼，确认不要了再删。

两个细节：

- **顺序不能反**（先导出、再删）。反过来的话，导出一旦失败，记录已经没了。
- 删的要是**当前正在聊的那个会话**，她会自动切到还剩下的最近一个。

**能恢复**（不然回收站就是个死胡同）：

```powershell
python -m divana.restore                            # 看看回收站里有什么
python -m divana.restore 20260920-201627-session-default.md
```

笔记是文件移动回去；会话是把导出的对话重新写回会话库。恢复成功后原件会挪进
`data/trash/restored/`——列表里不再出现（免得点两次变成两份），但也没删掉。

> 有个取舍要知道：**导出格式决定恢复的上限**。会话导出时只保留"人话"（用户和
> 助手说的话），工具调用和思考过程按设计就没存——所以恢复回来的会话，
> 对话完整、但看不到当时调过哪些工具。

> 删除是这个项目里唯一不可逆的操作，所以做了两层：二次确认 + 回收站。
> 弹窗用的是浏览器原生的 `confirm`——本地小工具够用，要做成产品再换自定义的。

## AI 早报（v0.9）

```powershell
python -m divana.digest           # 手动出一期
python -m divana.digest --if-due  # 给系统定时任务用（今天出过就跳过）
```

或者打开网页的 **AI 热点** 页，点"现在抓一期"。每天一期，存在
`vault/digest/YYYY-MM-DD.md`，页面上按日期列出、点开看。

机制和复盘完全一样（间隔判定 + 后台任务 + 失败留痕），只多一个设计选择：
**搜索工具交给早报 agent 自己用**，不是我们写死几个查询词。它能同时看到画像和计划，
自己决定搜什么，比写死"AI agent 最新进展"这种泛词准得多。

它的规矩写在 `prompts/digester.md` 里：

- 查 2-4 次，查询词要贴着学习者的方向，**不许查泛泛的"AI 新闻"**
- 挑 3-5 条跟他有关的，**宁可少不要凑数**；再热的话题跟他无关就丢掉
- 每条说清"是什么 + 为什么跟你有关"，链接只能来自搜索结果
- 全文不超过 600 字（"这是早饭，不是午饭"）
- 最后给一条"今天可以动手的一件事"

它只挂了一个工具（`search_web`）：**工具给多了模型总会想用一下**，
而"帮你查一圈"的任务不该顺手改你的笔记或计划。

> 第一次打开服务时它就会抓一期（从没出过，所以判定为"该跑"）。要花几次搜索
> 加一次模型调用，大概十几秒。

## 练习：考考我（v0.12）

Divana 原来只会讲和记，不会考——而"学过"和"能答出来"是两回事。v0.12 补上了
学习闭环的最后一环：

```
他说"考考我"  →  她出题（3~5 题，来自你的计划和笔记）
              →  你自己答（就用聊天）
              →  她说"批改"：逐题判定（对 / 半对 / 错）+ 漏了哪个要点
              →  错题自动写进「复盘记录」，错得多的主题进画像的「薄弱点」
```

两条设计取舍：

- **不做第二个 agent。** 出题和批改都由她本人做——题目和参考要点本来就在她视野里
  （她刚读完计划/笔记），再起一个 agent 只会多花一轮钱（4~6k token）而不会更准。
  对比：复盘、早报必须另起 agent，因为那两件事的素材**不在**她视野里。
- **每道题必须带参考要点**（存进 `data/practice.json`，**不念给你听**）。没有要点，
  批改就只能凭印象给分——那正是要避免的。有要点之后，"差一个关键点"会被如实判成
  **半对**而不是"挺好"，这也是评测里那条"批改判了错或半对"断言的依据。

数据落在 `data/practice.json`（当前这一测：题目 + 判定），错题汇总追加进
`vault/plan.md` 的「复盘记录」——**闭环的产物一定落在她自己会读到的地方**。
**网页上也能做**（第 6 页「练习」）。界面上就是：出题 → 每题一个输入框 → 提交批改 → 三色判定。三个端点：

```
GET  /api/practice        当前这一测（题目 + 判定 + 成绩；没有题目时返回空状态）
POST /api/practice/quiz   出一份（body: {"topic": "RAG 的切分"}）
POST /api/practice/grade  提交批改（body: {"answers": "第 1 题：…\n第 2 题：…"}）
```

它们**不自己实现任何逻辑**：出题就是替你说一句"考考我 xxx"，批改就是替你发一句
"我的答案：…"，然后走**同一条对话通路**。好处是 prompt 和工具只有一份——以后改规则，
聊天和网页同时生效，不会出现"网页版偷偷弱一点"。

一句话说清这一层的设计：**网页上的每个动作 = 一段程序合成的"用户输入"，喂给同一条对话通路**。
所以页面上出的题、批的改，和你自己在聊天里说"考考我"是**同一套逻辑**——prompt 和工具只有一份，
不会出现"网页版偷偷弱一点"。页面上那句合成的话在 `web/quiz.js` 的 `formatAnswers` 里（单独一个文件、
不碰 DOM，所以能用 node 测）：**没答的题也照样发过去**（写成"（没答）"），不然成绩就只按答过的算，
等于替你把自己不会的藏起来了。

> 一个取舍：**你的答案不落盘**，只留在页面本地（刷新就没了）。值得沉淀的是判定和错题——它们进
> 「复盘记录」和画像；答案本身是这一轮的输入，存下来只是多一份会过期的数据。

配套加了一个 `read_quiz` 工具，解决一个真问题：**跨会话批改会瞎判**。
她判分要看着参考要点，而要点只出现在出题那一轮的上下文里——你在网页上提交答案时
可能已经换了会话，手里没要点就会凭印象给分（那就是放水）。所以 prompt 里写死：
批改前手里没有题目和要点，先 `read_quiz`。


### v0.12.2：为什么"点了没反应"

练习页做出来的当天，报障是这么一句话：**"我点「出一份」，页面没反应。"**
查下来服务端、HTML、接口返回全是对的（`/api/practice` 明明返回了 5 道题），
于是这件事的价值全在"为什么会看不到"上。三个原因，三个教训：

**一、浏览器替我们做了决定。** 静态文件和接口响应都没带 `Cache-Control`，
浏览器遇到这种响应会**自己猜**一个缓存期（常见算法是文件年龄的百分之十）——
本地开发时就是几小时不问服务器一次。于是"我改了代码、页面还是老样子"，
看起来像 bug 没修好，其实是根本没跑到新代码。
修法是一个二十行的中间件 `FreshResponses`：页面和静态文件用 `no-cache`
（不是不缓存，是用之前先问一句"变了没"，没变回 304、一个字节都不重传），
`/api/` 的数据用 `no-store`（连存都别存）。
**本机一个人的服务，新鲜永远比省流量值钱。**

**二、出了错没人喊。** 脚本里一行报错，浏览器只在 console 里小声说一句，
页面上的表现是一片安静——用户看到的就是"没反应"三个字，查起来全靠猜。
所以现在：任何脚本错误都会在页面顶上顶出一条红带（截图即可排查）；
渲染那一步单独包了 `try/catch`，炸了就把原因写在题目区；
顶上那行状态也不再是空的，而是"RAG 基础 · 5 题，等着你答（时间）"。
**能自己报错的页面，才配叫能调试的页面。**

**三、对话和页面之间没有桥。** 他在聊天里说"考考我"，她确实把题出好、也落盘了，
但他不知道要去哪一页看。这个洞不是靠 prompts 里加一句"记得告诉他们去练习页"
来补的——她调了哪个工具，前端在 SSE 里**看得见**。所以现在她一出题 /
一批改，对话里就长出一个按钮：「题目出好了，在练习页 → 去练习页」。
**能由程序确定做到的事，别交给模型去猜。**

顺手修掉一个同类的洞：你正在练习页写答案，切去看看计划再切回来（或她刚在对话里
动过练习），页面会重画——原来的实现等于替你把答案删了。现在重画前先把答题框里
的文字捞回内存（`harvestAnswers`）。**重画之前先存用户输入**，这条以后做任何
带表单的页面都用得上。

这一轮也给"前端坏了"补了网（`tests/frontend_harness.mjs`）：用假 DOM 把
`markdown.js` / `quiz.js` / `app.js` 按浏览器的顺序真跑一遍，喂一份真的练习数据，
然后检查题目有没有画出来、答题框有几个、报错时红带有没有出现。
它补的是静态检查的盲区——id 都对、函数名都对、语法也合法，运行时照样能炸。

```powershell

python -m divana.evals --only repo-read,paper-read
python -m divana.evals --history       # 只看台账：成功率和单次成本的趋势（不花钱）
python -m divana.evals --calibrate     # 只看护栏校准表：max_tokens 该写多少（不花钱）
```

> `--only` 时**不会**存 baseline（`--save` 会被忽略并说明原因）：那份 baseline
> 只会有这次跑过的几条，其余用例的历史记录会被抹掉，下次跑全量时它们会显示成
> `[新增]`，看着像一次大改。要存就等一次全量跑。

用例在 `evals/cases.yaml`。一条只写四件事：**给她什么、必须做什么、禁止做什么、上限多少**。

```yaml
- id: repo-read
  question: 帮我看看 openai/openai-agents-python 这个项目
  expect_tools: [read_github_repo]    # 必须调
  forbid_tools: [search_web]          # 不该调（有 API 就别去抓网页）
  check_citations: true               # 顺便查引用是不是编的
  max_tool_calls: 4                   # 上限
```

判"她说了什么"有两层，能用下面那个就别用上面那个：

- `expect_any`：**词表**。好写，但只能判措辞——她换个说法就被误判成失败。
  而且词表加词带副作用：往里面加"输入错误"想放宽，等于把"她反过来指责用户打错字"
  也放行成了通过。
- `expect_pattern`：**正则**。判的是结构，措辞怎么变都能过。列表里的每一条都要命中。

```yaml
- id: empty-search
  expect_tools: [search_web]
  expect_pattern:
    - label: 如实说没搜到
      pattern: '(没|未|不)[^\n]{0,60}(结果|找到|搜到|相关|有关|一条|任何|资料|信息|内容)'
```

> 这条用例来自一次真实误判：她答的是「结果里**没有一条**跟「zzqqxxyy」…有关的东西」，
> 意思完全对，但当时的词表（没搜到 / 没有结果 / …）一个都没命中，用例被判成了失败。
> **那次是尺子不准，不是她退化。**改成"否定词 + 结果词出现在同一行"之后，措辞怎么变
> 都能过；原话记在用例的 `note` 里当回归样本，也有测试专门盯着它。

断言分三层，从过程看到结果：

| 层 | 字段 | 判什么 |
|---|---|---|
| 轨迹 | `expect_tools` / `forbid_tools` / `max_tool_calls` / `max_calls_per_tool` / `max_llm_calls` | 她**做了什么** |
| 文本 | `expect_pattern` / `check_citations` | 她**说了什么** |
| 产物 | `expect_files` | 她**改对了没** |

第一层最稳最便宜，第二层要看措辞（所以用正则判结构），第三层才是真正落到结果上的。

```yaml
- id: plan-update
  expect_tools: [update_plan]
  forbid_tools: [update_learner_profile]   # 改计划就只是改计划
  expect_files:
    - path: plan.md
      contains: ['[x] 自己写一个最小 agent', '阶段一']
```

`max_calls_per_tool` 也有，但它只该用来卡"**同一个工具重复调**"——比如追问时把同一个
仓库重读一遍（总次数上限 5 是拦不住这件事的）：

```yaml
- id: followup-stays-on-topic
  max_calls_per_tool:
    read_github_repo: 1
```

为什么要有第三层：**调了 `update_plan` 不等于改对了**。她完全可能把整份计划覆盖、
丢了一半内容——只看工具调用是发现不了的。

> 这里踩过一个坑，值得单独记：一开始给 `plan-update` 卡的是"`update_plan` 最多调 1 次"，
> 结果**错怪了她**——`update_plan` 的接口一次只能改一节，要动两节就得调两次。
> **断言和接口打架的时候，该改的是断言**（或者去改接口，别去改 prompt 逼她绕）。
>
> 后续（v0.11）：我们选的是**去改接口**——`update_plan` 现在一次能传多节。
> 于是"同一个工具只调 1 次"这条断言**从错变成了对**：她要动几节就一次写完，
> 3 次模型调用（读计划 + 改计划 + 回答）就能过。**这就是"接口设计诱导行为"的完整闭环**：
> 先是接口逼她绕圈，被发现后改了接口，最后连断言都跟着变合理了。
>
> 姊妹坑：**提问和断言也要自洽**。有一条用例问的是"用两句话讲讲什么是 embedding，
> 我在复习"，断言却是"讲完必须问一句要不要存笔记"——提问里既要求简短又暗示他已经懂，
> 等于在说"别啰嗦"，却又要求她多问一句。她照做才是对的（prompt 本来就有豁免：
> "用户只是想快速确认一件事时，直接回答，不要套模板"）。提问现在换成了真的在学新东西
> 的场景。**稳定地挂（每次都挂）通常就是这个信号：规则冲突或断言和输入打架，不是波动。**
>
> 第三次同类错误，这次是**断言 vs prompt 规则**：那条用例 forbid 了
> `update_learner_profile`，可 prompt 明说"反复卡在哪"就该记进画像。三次教训合起来
> 就一句话：**写断言之前先回去读一遍 prompt 和工具签名**——期望跟它们打架时，输的
> 永远是断言。
>
> 第四个坑最隐蔽，而且它不是断言的问题，是**测量**的问题：**"她说了什么"要按顺序收全。**
> 模型可以在"要调工具"的那次响应里先把话说完再调工具（实测那次讲解约 700 token），
> 而 `result.final_output` 只保留**最后一次**模型调用的文本——只取它，那段正文就没了，
> 于是"她其实答了"被误判成"她没答"。这次就被骗了一轮，还基于误判改了 prompt。
> 现在 `Outcome.text` 收的是这一轮**所有** assistant 文本（按顺序拼），
> 轨迹里也按"说了什么 → 调了什么 → 又说了什么"的原始顺序留着。

`expect_files` 读的是**临时 vault**（跑完趁临时目录还在，先拍一张文件快照），
所以照样碰不到你真实的笔记和计划。`path` 支持 `notes/*.md` 这样的通配；匹配到多个
文件时，只要有一个满足全部条件就算过（不然她多存一篇就会被误判）。

上限分两层，**别混着用**：

- **行为指标**：`max_llm_calls`（模型调用次数）、`max_tool_calls`、`max_calls_per_tool`。
  一次用户输入往往触发好几次模型调用（每调一次工具都要再问一次模型），所以
  `max_llm_calls` 才是"她绕了几圈"的直接度量——稳定、可解释。**该不该挂看这几个。**
- **成本护栏**：`max_tokens`。它会被模型推理开销（实测占 output 的 36%~75%）和输入
  长度带得上下飘，同一条用例能差一倍，**不能拿它当行为断言**。它的数值按
  `调用上限 × 该用例实测单次成本` 再留约 20% 余量；只调高不调低，保证它不比行为
  上限更紧。它挂了的意思是"比最坏的合法路径还多花 20% 以上"，值得查。

  **但它会过期，而过期时会假报回归。** 人格 prompt 和工具定义**每次调用都要重发**，
  所以每加一个工具，所有用例的地板价一起上移——而护栏是按写它那天的开销算的。
  2026-10-15 就有两条是这么挂的（只超 2% 和 21%，行为完全正常）。现在这种失败会
  自己把该有的数算出来（见下面那一节），不用再靠人手算一遍。

> 2026-09-24 的教训：这两层原来混在一个 `max_tokens` 里，于是 `plan-update` 和
> `no-unprompted-note` 的失败看起来像"她太啰嗦"，实际是"上限卡在了两种合法行为
> 中间"。拆开之后，绕圈由 `max_llm_calls` 精确抓，成本只负责防爆表。

用例还能覆盖配置，用来造"工具挂了"的场景——不必真去搞坏一个 API key：

```yaml
- id: tool-failure-honest
  given:
    settings:
      search_api_key: ""              # 搜索工具会正常地失败，然后看她怎么反应
```

这条也是从真实失败里来的：2026-09-13 那天搜索 key 没配好，她凭**通用经验**编了一串
排查步骤（还建议"去代码里搜 `DIVANA_SEARCH_API_KEY`"）——可她当时并没读过这份代码。
把"工具失败"当成"我能自己推理出原因"，是 agent 很典型的坏行为。

**读数只用"用例通过率"，不要用"运行次数"。** `--attempts 3` 下 18 条 = 54 次*运行*，
但报告里的 `passed` 数的是*用例*，规则是"三次全过才算过"。所以"45 次里挂 1 次"
该读成 **14/15 用例通过**，不是"98% 通过"——后者把同一条用例的抖动洗掉了，
写进简历或汇报里会被追问"这个数怎么算的"。

`baseline.json` 里记的 `commit` 取自 HEAD，**工作区有未提交改动时会带上 `+脏`**。
不然你会把"这一版为什么是 14/15"记到一个并不包含你那份 prompt 的提交上，回头复现不出来。

> 这个标记本身也修过两次，两次都是同一类毛病——**自己的产物把自己标脏了**：
> 先用 `--untracked-files=no` 排掉未跟踪的 `baseline.json`；后来发现存过一次之后
> 它变成**已跟踪**文件，于是第二次跑又被标成 `+脏`（2026-10-15 两跑全绿，第二次
> 记的却是 `b399d9e+脏`）。现在 `baseline.json` 和 `history.jsonl` 都排除在判断之外。
> 为什么较真：台账是拿去说事的东西，一个看不出原因的 `+脏` 会让读的人以为
> "这版 prompt 改过还没提交"，那正好把这一列的意义抵消掉。

**第一版只做确定性检查**：它零成本、零噪声、可重复，而且判的是**轨迹**
（她做了什么），不是文风。模型裁判留到以后——它贵、有噪声，判"事实对不对"最不可靠。

三个设计点：

- **隔离是结构上保证的**：每条用例在自己的临时目录里跑，画像 / 计划 / 笔记 / 会话库
  全是新建的，跑完就删。所以评测**绝不会碰你真实的学习记录**——哪怕某条用例让 agent 去写文件。
- **引用真实性是唯一能自动判的幻觉检查**：prompt 里写着"链接只能来自搜索结果"，
  而"编出处"恰好是 agent 最常见的幻觉形态。检查方式是把回答里的 URL 抠出来，
  逐个核对是否出现在工具返回里（有测试专门盯着它）。
- **报告的重点是对比，不是分数**：`[回归]` 那一行才是评测存在的意义——原来能过的现在挂了。
  另外每次都记录工具调用次数、模型调用次数和 token，因为"答对了但绕了八圈"也是一种退化。

**没过的时候会写出完整轨迹。** 报告只告诉你"哪条断言挂了"，看不出她**绕到哪去了**。
所以失败的那几条会各写一份 markdown 到 `evals/trajectory/`，里面有：

```
这一轮你说了什么
  → 每次工具调用的名字、参数、返回（返回值截断到 900 字，会标出原长度）
  → 她这一轮最终说了什么
跑完之后临时 vault 里的文件长什么样
```

查"同一个工具调了三次""答到一半跑题""文件里到底写成了什么"，都得靠它。
终端上也会顺手打一行工具序列，一眼能看出绕圈：

```
  [挂] plan-update　0/1　工具 3 次　15726 tokens
        工具轨迹：read_plan → update_plan
        完整轨迹：D:\CodexProjects\divana\evals\trajectory\plan-update.md
```

```powershell
python -m divana.evals --trajectory all    # 连过的也写（改 prompt 前后对着看很好用）
python -m divana.evals --trajectory off    # 不写
```

这些文件同名覆盖、不进版本控制（在 `.gitignore` 里），属于运行产物。

**成本要能拆开看。** 因为"超过 token 上限"这种失败，光看总数等于没看。跑完会打一张表：

```
token 分布（按合计从大到小）：

用例                    调用  input    output  合计     最贵一次  工具返回   上限
plan-update             4     16515    1538    18053    34%       337 字     22000
no-unprompted-note      2     7611     4285    11896    66%       23 字      12000

合计 29949 tokens　平均每条 14974　（input 占 81%）
```

每次模型调用的 input/output、每个工具返回的体量、最后那段回答的体量，都写在轨迹文件里
（`--trajectory all` 全拿）。

两个口径必须说清：

- **一次用户输入 ≠ 一次模型调用。** 她每调一次工具都要再问一次模型，所以"4 次调用"
  是正常的——成本要按**调用次数**算，不是按轮次。
- **推理 token 也计费。** 有的模型把"思考"算进 output，说话少不代表不花钱。明细表里
  单列了一列"其中推理"，就是这个原因。

还有个必须知道的**固定成本**：每次模型调用都要重发一遍 instructions（人格 + 日期 +
画像），这份项目现在是 3572 字符 ≈ 1800 token；再加工具定义的说明（约 1300 token 的
下限）。**这个底噪乘上调用次数，就是每条用例的地板价**——所以"少调一次模型"通常比
"少说几句话"省得多。

2026-09-26 把这两项**实测**了一遍（`python -m scripts.check_env` 会打出来）：

```
固定开销: 全部工具的 schema + 说明合计 4674 字符（每次调用都重发）
人格 prompt: 3185 字符（约 1563 token，每次调用都重发）
第一次调用的 input 实测 4248 token
```

也就是：**工具定义 ≈ 2490 token/次 + 人格 ≈ 1630 token/次 ≈ 4300，和实测的 4248 对上**。
乘 33 次调用 ≈ 14 万 token，而整份评测集实测 168,117 → **固定开销占 83%**。
她真正读的、写的、想的，只占 17%。

**所以成本优化的杠杆是有顺序的**：① 少调一次模型（4248/次，比整个人格 prompt 还贵）；
② 按需拼 prompt（"总结材料" + "查资料"两节共 960 字符，但要有场景判断，漏了就行为退化）；
③ 抠字（把工具说明和 prompt 里"给读代码的人看"的部分去掉，实测省了 306 字符 ≈ 150 token/次）。

**而且要知道什么时候停手**：继续抠字最多再省 80 token/次，可验证一次改动要跑一遍全量
评测（168k token）——投入产出是负的，除非调用量足够大。这轮就是这么收的：能确认省掉的
省掉，其余明说"不值得做"。


记账本身还修过一个 bug：多轮用例原来每轮**覆盖**统计，只报了最后一轮的钱（成本被少算），
而 `max_tokens` 又是拿它比的——等于那条用例只卡了最后一轮。现在改成累计。

还有一个口径要对齐：`--attempts 3` 时，**断言、成本、轨迹都取自失败的那一次尝试**
（不是最后一次）。否则一份轨迹里会出现"成本 5335"和"实际 13468"打架——前者来自最后
一次、后者来自失败那次，排查成本问题时最容易被它误导。

加用例最好的方式：**某天发现她答错了，就把当时那句话抄成一条**。那是回归用例，
比手写合成的有价值得多——这句话也写在 `evals/cases.yaml` 的开头。


### 两件能被追问的指标：端到端成功率 + 单次成本

上面几节解决的是"这次改动有没有弄坏东西"。这一节解决另一个问题，也是面试里一定
会被追问的那个：**它到底多准、多贵？** 这两个数要能张口就说，还得说得出处。

```powershell
python -m divana.evals --history   # 看趋势（不需要 API key）
```

（下面这张表是**示意**，真数字来自你自己的运行——单价对不对，报告里会写。）

```
评测台账（最近 2 次，共 2 次）：

时间              提交          题集       成功率        单条 token   单条成本    总成本
2026-10-13 22:40  3446d40       6f09dba2   20/20（100%） 8405         ￥0.0076    ￥0.1523
2026-10-15 11:20  736185f       6f09dba2   20/20（100%） 8180         ￥0.0074    ￥0.1480

最早那次 → 最近一次：成功率 20/20（100%） → 20/20（100%）；单条成本 ￥0.0076 → ￥0.0074（-3%）
```

**每次全量跑都会往 `evals/history.jsonl` 记一行**（`--only` 不记：半截数据的成功率会
凭跑了几条上下跳，看着像她在退化）。台账是 JSONL——一行一条，追加不重写，
坏一行也读得出其余的。

**"固定题集"靠判据指纹来证明。** 光说"题集很稳定"没有用：`cases.py` 会给每条用例算
一个指纹，把**所有影响通过与否的东西**（提问、给定材料、每一条断言、每个上限）摊成
文本再哈希。于是——

- 改了判据 → 报告里出现 `[尺子] 这 2 条的判据改过了：plan-update、quiz-from-material`
  ——先确认是你有意改的，再去解释分数；
- 只改给人看的字（`note`、断言的 `label`）→ **不报警**。算进去的后果很实际：
  润色一段注释就喊一次"尺子变了"，喊上三次就没人看这个警告了，等真改了判据反而被忽略；
- 列表类字段排序后再算（"每条都要命中"和顺序无关），重排一下不该报警。

**成本是钱，不是 token。** token 数几乎不能直接比：输出单价通常是输入的 3 倍，
命中缓存的输入又只有未命中的十分之一左右。所以 `divana/evals/pricing.py` 把每次
调用折成钱，单价从 `.env` 读（`DIVANA_PRICE_IN / _OUT / _CACHED`，单位是元/百万
token；不填就用内置默认值，**报告里会把"价格来源"打出来**——一个不知道单价的成本
数字没人敢引用）。

> 缓存那一项不是细节，是主要矛盾：人格 prompt + 工具定义每次调用都要重发
> （约 4300 token），而它们基本都命中缓存。按未命中价算，这部分会被算贵十倍。
> 服务商不报命中数时（那就是 0），整份 input 按未命中价算——**宁可高估，不要低估**：
> 估高了你只是保守，估低了你会在账单上发现真相。

> 这一轮还踩了个纯 Windows 的坑：报告里写半角 `¥`，`print` 直接抛
> `UnicodeEncodeError`——中文控制台是 GBK（cp936），它编得出全角 `￥`，编不出半角
> `¥`。**不是显示成问号，是整条命令崩掉**，报告一个字都看不到。现在符号用全角，
> 另外给 stdout 加了 `errors="replace"` 兜底：宁可一个符号难看，也不要整份报告消失。


### 三条挂了的用例，三种不同的病

2026-10-15 第一次真跑这份台账：**17/20（85%）**，成本 ￥0.3926。三条挂了，
而它们**没有一条是她退化**——这是这一节存在的理由：报告说"挂"，不等于她错了。

**病一 · 尺子过期（2 条：`followup-stays-on-topic`、`quiz-from-material`）**
挂的是成本护栏：24,484 > 24,000（超 2%）、21,750 > 18,000（超 21%）。
证据全在报告里：行为上限一条没超（调用 3 次、上限 4 次），轨迹里仓库也只读了一次
（那条用例专门卡的就是"别重读"）。**她没做错任何事，是护栏按旧开销写的。**
根因就是上面那句话：每次调用都要重发人格 prompt + 全部工具定义，而 v0.12 一次加了
三个工具（`make_quiz` / `grade_quiz` / `read_quiz`），地板价整体上移。
修法是按公式把护栏抬上去——**并且把算式写进用例的 `note`**，让下一个人看得出这个数
是从哪来的：

```yaml
  max_tokens: 39000     # 4 × 8161 × 1.2，2026-10-15 按实测重算
```

顺手改掉了一件事：这种失败现在**自己给出该有的数**，因为"实际 24484"本身
没法告诉你下一步该干嘛。

```
- **token 不超过 24000**
    - 实际：实际 24484（超 2%，跑了 3 次调用、单次均值 8161；
      按「调用上限 4 × 单次 × 1.2」该是 39000）
```

**病二 · 用例没给材料（`quiz-graded-into-review`）**
它要的是"出题 → 他答 → 批改"，可这条用例**没有 `given.plan`**——她手里什么都没有。
轨迹里她的原话："出题只能基于你实际接触过的内容，不能凭空塞一道题给你，那样可能
正好考到你没学过的东西"。于是她先反问"你学到哪了"；第二轮的"我的答案：…"便被她
当成了**用户的一个观点**，她据此出了一道验证性的题，从头到尾没有可批的东西。
**她做得对，用例写错了**——`expect_tools` 要 `make_quiz`，人却没给她素材。
修法是补上 `given.plan`（和 `quiz-from-material` 同一份材料），并把这段经过写进
用例的 `note`。

> 这已经是**同类教训第三次**现身了（前两次：断言卡住 `update_plan` 的调用次数、
> 提问里既要求简短又要求多问一句）。一句话总结：**断言（或给定材料）和输入打架时，
> 输的永远是断言。**稳定地挂 = 规则冲突，不是波动。

**病三 · 评测自己的测量 bug（工具返回挂错了调用）**
轨迹里 `read_plan` 的返回写着"没找到和「RAG 切分」有关的笔记"，而 `search_notes`
的返回是**计划正文**——两个工具的返回整体互换了。根因在评测自己的代码里：模型
**一次要求并行调两个工具**时，两次调用挨在一起，两个返回按序回来，而挂载用的是
"最近一次还没返回的调用"——第一个返回就被挂到了第二个调用上。
修法是按 `call_id` 精确配对（适配器不给编号时退回老办法，那时串行仍然是对的），
并补了单测：并行不互换、返回顺序颠倒也对、没有编号时串行照样对。

> 教训：**评测工具本身也要被怀疑。**这是第三次了——前两次是"多轮只算了最后一轮的钱"
> 和"工具归因挂错调用"。判分体系一旦串行，它给出的每个结论都跟着错，
> 而你还会因此去改本来没问题的 prompt。

顺带一个好消息：这轮 92% 的 input 命中了缓存（241,024 / 262,645），
所以按未命中价算会得出 ￥1.24——**实际 ￥0.39，差了 3 倍**。
这就是定价那一轮坚持把"命中"单列的理由。

### 第二次全量跑：18/20，这次是"随机挂"

同一批用例，`--only` 单跑时三条全过；半小时后全量跑，那两条里又挂了一条半。
**同一个 commit、同样的输入、结果不同——这不是退化，是采样抖动。**

两次的挂法也不一样，轨迹里看得清清楚楚：

- `quiz-from-material`：这次她**拿到了材料**（原话里复述了那条勾掉的里程碑），
  但还是先反问"你最近是在学 RAG 吗？具体学过哪些？"——没出题。
- `quiz-graded-into-review`：她只搜了笔记（空的），就断言**"你的画像、笔记、学习计划
  目前都是空的"**——而计划里明明有材料，她**根本没读**（`read_plan` 一次都没调）。

两条的共同点：她卡在同一个两可的读法上——"材料够不够，要不要先问清楚"。
prompt 说"题目只能来自真材料"，却没说**材料要从哪几处找、有多少算够**，
于是模型就在"先出题"和"先反问"之间随机。

**判据（记住这个分岔）**：稳定地挂 = 规则冲突或断言和输入打架，去改规则；
随机挂 = 行为边界模糊，去把边界写死。这次是后者，所以改的是 prompt，不是断言——
把断言放宽（允许她先反问一轮）等于把要求悄悄降下来，而他明确要的是"考考我 = 出题"。

改完是这样（`prompts/divana.md`）：

```
- 说"我这边没有材料"之前，**先把计划读一遍**（`read_plan`）：笔记里搜不到不等于没材料
- **有一处材料就出题**（哪怕只有一条勾掉的里程碑），细节不够就出成开放题
- 三处**全都**空的时候才说"我手边没有材料"，并且给他两条路
```

顺带修了同一节里一句过期的话（"这四条要守住"——早就是六条了，现在七条）。

> 这一轮另外两件事是好的：轨迹里的工具返回**终于配对正确**了（`read_plan` 的返回这次
> 真的是计划正文），说明上一轮那个测量 bug 修对了；成本护栏也一次都没响
> （那条回归用例 22,890 < 39,000）。

### 第三次全量跑：19/20，这次是"说了但没落盘"

`quiz-graded-into-review` 变成 `[修好]`（上一轮那三条 prompt 规则生效了），
只剩 `quiz-from-material` 还在随机挂：`--attempts 3` 单跑 3/3 过，全量跑又挂一次。

这次的诊断藏在**两条断言的组合**里——同一次运行里，一条过、一条挂：

```
· 把题目真的问出来了          ← 过（她确实问了）
· 调用过 make_quiz            ← 挂（实际调用：read_plan、search_notes）
```

轨迹里她的原话是"考考你：文档切分与检索 …… **第 1 题**（切分的动机）……"。
**题目是真的问了，但一次工具都没调。**

这不是"工具断言太严"，后果很具体：题目只活在聊天记录里 → **练习页空着**
（那一页读的是 `data/practice.json`）→ 等他答完，她手里**没有参考要点**
（`read_quiz` 也取不到）→ 只能凭印象判"半对"——整个闭环断在最关键的一步。
而用户**当场看不出问题**，要等到批改那一步才会表现成"她好像不太会判"。

她为什么这么干？原话里有一句"都是开放题"。推测是这个推理：开放题没有标准答案，
所以不用存要点。而"**开放题也要要点**"确实是规则里的空白——判"半对"就是拿要点对出来的。

修法两处，都在"让她非落盘不可"上：

```
prompts/divana.md   出题必须调用 make_quiz——把题目直接打在聊天里不算出题；
                    参考要点只有它存得下，练习页也只读它存的题。开放题同样要有要点。
tools.py            make_quiz 的说明里同样写清："直接把题目打在回复里不算出题"
```

顺带把**量法**补硬了：这两条用例各加一条产物断言，直接看那份文件里有没有东西——
`practice.json` 里要有 `"points"`（题目和要点真的存了）/ `"answers"`（他的答案和判定存了）。

> 教训：**"她做了但没落盘"比"她没做"更危险**，因为它看起来是对的。要抓住它，
> 断言必须落在**产物**上——她说了什么只能当线索，文件里有没有才是事实。

### 第四次全量跑：两条老用例假报回归——护栏过期（第四次）

`quiz-from-material` 那两条好了，但换了两条老的挂：`version-needs-search`
（23,421 > 16,000）和 `note-search`（19,035 > 19,000，**超 0.2%**）。

这两条**跟上一轮改的 prompt 毫无关系**——它们是同一个老病：护栏是照 v0.10 那天的
开销写的，而"每次调用的固定开销"一直在涨（v0.12 加了 3 个工具，上一轮又往 prompt
里添了 4 行规则）。**护栏是这套评测里唯一会过期的断言。**

上一轮加的那句话正好接住了它——不用再手算：

```
· token 不超过 16000
    实际：实际 23421（超 46%，跑了 3 次调用、单次均值 7807；
    按「调用上限 3 × 单次 × 1.2」该是 28000）
```

所以这次不再一条条等它撞。加了 `python -m divana.evals --calibrate`
（读上一次的实测数据，**不需要 API key**），对着它把 20 条全算了一遍：
**18 条本来就偏紧**，一次性改到位（只调高不调低）。校准命令只**建议**、不改文件
——护栏是判据，动它要人点头。

```
$ python -m divana.evals --calibrate
这 18 条比实测该有的还低——**迟早会假报一次回归**，建议改成：

用例                      实测     调用  上限    建议    单次均值
no-tool-concept           6259     1     10000   15000   6259
version-needs-search      23421    3     16000   28000   7807
note-search               19035    3     19000   23000   6345
…
```

> 代价要说清楚：护栏放宽之后，"防爆表"的属性还在（某个工具一次返回五万 token
> 照样会响），但"她绕了多少圈"的灵敏度下降了——**那件事本来就该由 `max_llm_calls`
> 管**。两个断言不该互相代劳：代劳的结果就是它们打架，而打架时输的永远是护栏。

### 收尾：连续两次 20/20

改完当天晚上跑了两次，都是 **20/20**，成本 ￥0.373 和 ￥0.364，单条平均约 14.9k token。
