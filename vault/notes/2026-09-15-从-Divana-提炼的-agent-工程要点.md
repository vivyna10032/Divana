# 从 Divana 提炼的 agent 工程要点

## 这是什么

Divana 是一个命令行 AI 学习助手。剥开看就四样东西：**人格 prompt + 工具 + 三层记忆 + 一个对话循环**。读它的源码，能提炼出几个可迁移到任何 agent 项目的工程要点。

## 要点一：记忆要分层，标准是"要不要常驻眼前"

| 层 | 存在哪 | 怎么进模型 | 设计逻辑 |
| --- | --- | --- | --- |
| 学习者画像 | `vault/profile.md` | 每轮拼进 system prompt | 必须一直在眼前 → 所以必须**小** |
| 学习笔记 | `vault/notes/*.md` | 不进上下文，靠 `search_notes` / `read_note` 按需取 | 可以有很多 → 所以**不占窗口** |
| 会话存档 | `data/divana.db` | 只带最近 N 条（`HISTORY_LIMIT`） | 全量记录，带多少进模型有限制 |

核心权衡：**什么塞进 prompt、什么做成工具按需查，是 agent 工程里最核心的权衡**。

## 要点二：工具是"给模型的说明书"

模型看不到函数体，只能看到**函数名 + docstring + 参数 schema**，靠这三样决定什么时候调、参数怎么填。所以「改工具说明 = 改行为」，通常比改人格 prompt 更直接、更好验证。

声明和实现是两层，模型只信声明——声明了却没实现，模型照样会调，然后失败。

## 要点三：多 agent 的本质是「不同上下文 + 不同指令」

「回顾对话」要单独起一个总结者 agent，因为对话全文存在 `divana.db`，而主 agent 的上下文只有最近 N 条——它看不到自己的完整历史。

判断标准一句话：**素材在主 agent 眼前，就不需要第二个 agent；主 agent 看不到，才另起一个。**

多 agent 最朴素的形式不是「多个角色在聊天」，而是不同任务用不同的上下文和不同的指令。

## 要点四：把链路拆成能单独验证的段

`/search` 命令故意绕过模型，单独测「搜索本身通不通」，和「模型会不会去调它」分开验——否则永远不知道坏在哪一环。

排查「我明明填了 key 却没生效」这类问题，先看启动信息里的「配置来源」「联网搜索状态」两行。

工程习惯：**agent 出问题先拆开定位，别笼统说它坏了**。

## 要点五：成本刹车 + 安全边界

- `HISTORY_LIMIT` 是成本刹车：聊得越久成本越高，这个上限就是上限。
- 只允许 `http/https`、挡掉 `file://`：防网页里的恶意指令带着模型去读本地文件（prompt injection 的一种防御）。
