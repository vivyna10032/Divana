# Agent 学习路径与 Divana 源码探索

### 这次聊了什么

从验证 Divana 的联网搜索 key 是否生效开始，扩展到探索 GitHub 上适合练手的 agent 开源项目，最终落到用户（大三 AI 专业学生）的实习规划。核心结论是把"通过读 Divana 源码学 agent 开发"作为当前主线，并校准了学习目标——读懂设计而非交付功能。

### 关键结论

**工具声明的有效性验证**
- `.env` 配置改动后必须重启运行 Divana 的**进程**（不是重开窗口），因为环境变量在程序启动时读入内存。
- 验证方法：问一个"只有联网才能确认且模型自己没把握"的问题（如"Python 最新稳定版"），观察是否真的调用搜索并带来源链接。
- 验证结果：key 生效，Python 3.14 发布于 2025 年 10 月 7 日，是当前最新主要稳定版本。

**GitHub API 与仓库读取**
- `read_github_repo` 工具只返回「仓库元信息 + README 全文」，不会自动拉取代码文件内容。
- 匿名访问 GitHub API 有配额限制，403 不一定是仓库问题。
- 读具体代码文件需贴文本或给 raw 链接（`https://raw.githubusercontent.com/...`），用 `read_url` 抓取。
- 私有仓库默认读不到（匿名无凭证），可行办法：临时设 public、贴文件内容、或配 token（不推荐明文贴出）。

**从 Divana 仓库提炼的 5 个可迁移知识点**
1. **记忆分层**：分层标准是"要不要常驻眼前"。画像每轮拼进 system prompt（必须小），笔记不进上下文靠工具按需取（可以多），会话存档只带最近 N 条（`HISTORY_LIMIT` 控制成本）。
2. **工具是给模型的说明书**：模型只看到函数名 + docstring + 参数 schema，看不到函数体。改工具说明 = 改行为。声明与实现是两层。
3. **多 agent = 不同任务用不同上下文 + 不同指令**：主 agent 上下文只有最近 40 条，看不到完整历史（存在 `divana.db`），所以另起"总结者 agent"。判断标准：素材在主 agent 眼前就不需要第二个 agent。
4. **把链路拆成可单独验证的段**：`/search` 命令绕过模型单独测搜索本身；启动信息三行（配置来源、画像路径、搜索状态）用于定位"填了 key 却不生效"这类问题。这防止笼统判断"它坏了"。
5. **成本刹车 + 安全边界**：`HISTORY_LIMIT` 控制 token 成本；只允许 http/https、挡掉 `file://` 是 prompt injection 的一种防御。

**实习岗位真实要求**
- JD 关键词：Agent 工作流、Prompt Engineering、Function Calling / MCP、RAG、多 Agent 协同。
- 框架要求：LangChain / LangGraph / Dify / AutoGen / Graph RAG。
- 工程化标配：Docker、API 设计、数据库/向量库、CI/CD。
- 简历三维表达法：架构表达（loop、工具注册、上下文裁剪、记忆、错误恢复）+ 业务表达 + 结果表达（评测集规模、成功率、成本优化）。

**差距与里程碑**
- 用户有完整项目（稀缺资产），但缺"结果表达"：无评测集、成功率数字、成本数据。
- 两周四个里程碑：① 写架构说明 → ② 建 20 条评测集 + 算成功率/成本 → ③ 接入 MCP 或标准 function calling → ④ 用 LangGraph 重写核心 loop。
- 里程碑产出校准为"理解"而非"功能交付"。

**Codex 生成代码的正确用法**
- 心法：把 Codex 当写代码的同事，自己是 reviewer，不是验收人。
- 每块代码要回答三个问题：为什么存在？跟谁怎么协作？能不能换个更简单/更标准的做法？
